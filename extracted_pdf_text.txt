dẫn đến tình trạng khách đặt món nhưng thực tế nguyên liệu đã hết; thiếu cơ chế đối soát thanh

2.2 Task 2.2 – Sơ Đồ Tuần Tự (Sequence Diagram)
Tài liệu tham chiếu bắt buộc: docs/requirements/sequence-checkout.md và sơ đồ nguồn

Sơ đồ tuần tự mô tả chi tiết quy trình giao tiếp thời gian thực cho use-case trọng tâm "Đặt và
thanh toán đơn hàng" với đủ 5 Lifelines theo đúng chuẩn OMG UML 2.0 (được tách thành 2
phần để giữ chữ rõ nét khi in ấn):
Customer −→ Next.js UI −→ NestJS API −→ Database −→ Payment Service
2.2.1 Phân tích các giai đoạn tương tác tuần tự
1. Giai đoạn 1 – Khởi tạo phiên & Xác thực JWT:
 Client gửi HTTP Request: POST /api/orders kèm header Authorization: Bearer <JWT> và
payload chứa danh sách món trong giỏ hàng.
 JwtAuthGuard tại Backend giải mã chữ ký token bằng JWT_SECRET. Nếu token không hợp lệ hoặc
hết hạn, trả về ngay HTTP 401 Unauthorized.
2. Giai đoạn 2 – Mở Database Transaction & Khóa tồn kho nguyên liệu:
 Backend mở khối giao dịch prisma.$transaction(async (tx) => {...}).
 Truy vấn danh mục định mức nguyên liệu (ProductRecipeItem) của từng sản phẩm theo kích
cỡ được chọn.
 Khấu trừ nguyên liệu bằng tx.ingredient.updateMany với điều kiện stock >= needed (bảng
Product không lưu cột stock tĩnh).
 Kiểm tra và tăng trường version của sản phẩm bằng tx.product.updateMany({ where: {
id, version } }) để chống hiện tượng Race Condition (Optimistic Locking, tối đa 3 lần retry).
 Khởi tạo bản ghi Order ở trạng thái ban đầu là PENDING kèm danh sách chi tiết các dòng món
OrderItem và toppings đính kèm.
 Phản hồi mã HTTP 201 Created kèm thông tin đơn hàng vừa khởi tạo về cho Next.js UI.
3. Giai đoạn 3 – Xử lý giao dịch thanh toán & Cơ chế Idempotency Key:
 Trên UI Checkout (/checkout), Client gọi POST /api/payments/create-payos-link (VietQR)
hoặc POST /api/payments/momo-payment (MoMo). Riêng với đơn 0đ hoặc kịch bản kiểm thử
tự động, Client gửi POST /api/payments kèm orderId, số tiền, phương thức (WALLET / CARD)
và chuỗi định danh duy nhất idempotencyKey (UUID v4).
 Backend kiểm tra sự tồn tại của idempotencyKey trong bảng Payment:
– Nhánh xử lý lặp (Idempotent Hit): Nếu key đã được xử lý trước đó, hệ thống lập tức
hoàn trả dữ liệu phản hồi đã lưu (idempotent: true), không thực hiện trừ tiền lại hay thay
đổi trạng thái đơn hàng.
– Nhánh xử lý mới (New Request): Backend xác nhận qua cổng thanh toán (PayOS/MoMo
Webhook/IPN hoặc mock trong môi trường test).
4. Giai đoạn 4 – Phân nhánh kết quả thanh toán (Nhánh Alt):
 [Thanh toán Thành công]: Khi thanh toán được xác nhận, Backend mở transaction
cập nhật trạng thái đơn hàng sang PAID (bảo vệ chống trùng bằng updateMany kiểm tra
PENDING/PAYMENT_FAILED), tạo bản ghi giao dịch trong bảng Payment, cộng điểm thưởng và ghi
nhận vào bảng LoyaltyTransaction. Giao diện Client dọn sạch giỏ hàng và chuyển sang trang
/orders/:id.
 [Hủy đơn / Hết hạn hoặc Thanh toán Thất bại]: Khi khách hủy hoặc hết hạn 5 phút
(PATCH /api/orders/:id/cancel), Backend chuyển đơn sang CANCELLED và hoàn trả số lượng
Ingredient.stock đã trừ; nếu đánh dấu PAYMENT_FAILED, đơn chờ khách thử lại (/retry) hoặc
hủy để hoàn kho.

 Web Application (Frontend PWA): Ứng dụng Next.js 16 (React 19, Tailwind CSS 4, Zus-

3.1.2 Phân tích lý do lựa chọn, ưu điểm, hạn chế và sự đánh đổi (Trade-offs)
 Lý do chọn Modular Monolith thay vì Microservices: Hệ thống BrewLite phục vụ quy mô
chuỗi cà phê vừa và nhỏ với lưu lượng hàng nghìn đơn mỗi ngày. Việc lựa chọn Modular Monolith
giúp toàn bộ giao dịch đặt hàng, khóa giữ kho và thanh toán được thực thi trong một Database

microservices.
 Đánh đổi (Trade-offs): Toàn bộ backend được triển khai trong cùng một tiến trình (Single

5.3.1 Đặc tả 7 yêu cầu kỹ thuật trong Pipeline CD
1. Quality Gate nghiêm ngặt: Trước khi cho phép đóng gói, pipeline tự động chạy kiểm tra

PRODUCTION_API_URL và build cả Backend lẫn Frontend. Bất kỳ bước nào thất bại, pipeline dừng
ngay lập tức.
2. Tạo Docker Image gắn tag phiên bản: Docker Image được gắn nhãn định danh kép: commit
Git SHA (để đối soát mã nguồn), latest và Semantic Version (ví dụ: v1.0.1).
3. Đẩy Image lên Container Registry: Đẩy Docker Image đã đóng gói lên GitHub Container
Registry (GHCR) an toàn.
4. Triển khai vào Production bằng Secret: Sử dụng RENDER_API_KEY + RENDER_SERVICE_ID
(hoặc Webhook bí mật RENDER_DEPLOY_HOOK) lưu trong GitHub Secrets để kích hoạt Render kéo
image mới mà không để lộ mật khẩu.
5. Chạy Database Migration an toàn: Tuyệt đối không dùng lệnh prisma db push có nguy cơ
mất dữ liệu. Hệ thống sử dụng lệnh npx prisma migrate deploy trong chỉ lệnh CMD của Dockerfile
